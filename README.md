# 营业数据查询

针对现有 POS 数据库（MySQL 5.5 / PHP 8.2）的营业数据查询工具，**纯查询，不写库**。

功能：
- **登录密码保护**，密码写在 `config.php`
- 按日期区间统计营业额与人数，分**白天 / 晚上 / 全天**三档，也可只看当天
- 查询指定菜品在区间内的点单情况
- 点单最多 / 最少的 10 个菜品，以及**每个岗位**的最多 / 最少 10 个菜品
- **岗位（打印机）单量排名**
- **开台核对** —— 当前已开桌未结算的台，人数与套餐份数是否对得上；
  可人工确认并桌等例外，外带（Llevar）这类台自动免核对

菜品页的「岗位」下拉框有两种用法：
- **全部岗位**（默认）：先给出岗位汇总表，再**逐个列出每个岗位**的最多 / 最少 10 个菜品
- **选中某个岗位**：整页只统计该岗位，最多 / 最少 10 个都收窄到这个岗位内

岗位汇总表每行末尾都有「只看这个岗位」的直达链接。

菜名过长时会截断成省略号（全宽表格约 300px，岗位左右并排时约 170px），
**鼠标悬停可看到完整菜名**。截断只是显示层面的，导出或复制得到的仍是完整名称。

## 手机与电脑自适应

同一套页面，电脑、平板、手机都能用，不需要单独的手机版。

| 屏幕 | 表现 |
|---|---|
| ≥ 900px | 完整布局：表单横排、岗位排行左右并排 |
| 640–900px | 表单开始换行，岗位排行改为上下排列 |
| < 640px | 表单竖排、按钮通栏，导航换成短名（开台／营业额／菜品／岗位）并可横滑 |

针对手机做的处理：

- **开台核对**在手机上换成一台三行的紧凑列表（桌号+状态 / 人数·套餐·时长 / 金额·菜品·服务员），
  每台约 95px —— 这页最常在店里拿手机看，11 列横向滚动没法用。
  开 20 桌约 1900px，滑两屏就能看完；桌面仍是完整表格。
  两个视图共用同一个格式化函数，不会出现口径不一致
- 其余宽表格保持横向滚动，但**首列吸附在左边**，滑动时始终知道当前是哪一天／哪道菜
- 次要列（下单次数、菜品数等）在手机上隐藏，需要时横屏或用电脑看
- 输入框字号固定 16px —— 低于这个值 iOS 会在聚焦时自动放大整个页面
- 点击目标按**指针精度**（`pointer:coarse`）而不是屏幕宽度放大，
  这样 iPad 竖屏（768px，宽于手机断点）也能得到手指友好的尺寸

不依赖任何前端框架，纯 CSS 媒体查询，没有额外的 JS。

## 〇、登录

所有页面都要先登录。密码在 `config.php` 的 `password` 里设置，两种写法都支持：

```php
// 1) 明文，最简单
'password' => 'abc123',

// 2) bcrypt 哈希，更安全 —— config.php 被人看到也读不出原文
//    先执行：php -r "echo password_hash('你的密码', PASSWORD_DEFAULT);"
'password' => '$2y$10$....',
```

**留空则谁都登录不进去**（是全部拒绝，不是放行）。

其他细节：
- 会话 8 小时后过期，关闭浏览器也会失效
- 会话 Cookie 设了 HttpOnly，走 HTTPS 时自动加 Secure
- 登录成功后重新生成会话 ID，防会话固定攻击
- 登录表单带 CSRF 令牌；密码比较用 `hash_equals`，密码错误时统一延迟 1 秒拖慢暴力破解
- 右上角「退出」可登出

> **注意**：登录会用到 PHP 的 session，PHP 会把会话文件写到服务器的 session 目录 ——
> 这属于 PHP 自身机制，与数据库无关，本程序对数据库仍然只读。
>
> 这是一道**基础的门禁**，适合店内网使用。它挡得住随手打开页面的人，但不是抗攻击的
> 认证系统（只有一个共享密码、没有按 IP 封禁）。放到公网请务必套 HTTPS，
> 并考虑在 Web 服务器层再加一层访问限制。

`tests/checkdb.php` 从浏览器访问时同样要求登录（它会显示数据库信息）；
命令行运行不受影响。`tests/env.php` 不要求登录 —— 它是排障刚需，
必须在任何情况下都能打开，且不显示任何业务数据。

## 一、安全性：只做查询

程序**不会**对数据库做任何写入、删除或结构变更。三道防线：

1. **代码层**：全程序只有 `lib/db.php` 一个数据库出口，只提供 `select()`，
   没有 `exec()`、没有事务、不开启多语句执行。
2. **语句层**：每条 SQL 执行前都要通过 `assertReadOnly()` —— 必须以 `SELECT` 开头，
   不得含分号，不得出现 `INSERT / UPDATE / DELETE / DROP / ALTER / TRUNCATE /
   CREATE / REPLACE / GRANT / CALL / INTO OUTFILE` 等任何写操作关键字
   （注释会先被剥离，防止关键字藏在注释里绕过）。
3. **数据库层**（需要你配合）：请在 `config.php` 里填一个**只有 SELECT 权限的账号**：

   ```sql
   CREATE USER 'report_ro'@'%' IDENTIFIED BY '你的密码';
   GRANT SELECT ON coolroid.* TO 'report_ro'@'%';
   FLUSH PRIVILEGES;
   ```

   这样即使程序出任何问题，数据库也会直接拒绝写操作。

所有用户输入（日期、菜品 ID、就餐方式）一律走 PDO 参数绑定，表名走白名单校验。

## 二、安装

1. 把整个目录放到 Web 服务器可访问的位置。
2. 编辑 `config.php`，填入数据库地址、库名、只读账号密码，以及**登录密码**。
3. 浏览器打开 `index.php`，输入密码进入。

无需 Composer，无外部依赖，无需写权限（不产生任何缓存或日志文件）。

### 配置分两层（升级时很重要）

| 文件 | 放什么 | 升级时 |
|---|---|---|
| `config.php` | 数据库地址、账号密码、登录密码 | **不要覆盖** |
| `lib/settings.php` | 营业时段、套餐清单、免核对规则等**功能参数的默认值** | **直接覆盖** |

**升级步骤就一句话：除了 `config.php`，其它文件全传一遍。**

这么分是有教训的：`config.php` 装着密码，是你自己维护的，实际维护时基本不会
重新上传。功能参数如果只写在那边，新版本加的参数就永远读不到，
**功能会静默失效**（外带免核对就这么翻过一次车）。

想改某个功能参数时，**不要去改 `lib/settings.php`**（下次升级会被覆盖），
把同名的键写进 `config.php`，那边的值优先生效：

```php
// config.php
'day_end'         => '17:00:00',
'no_combo_tables' => ['Llevar*', '外带*', 'Barra*'],
```

`config.php` 里没写的键一律用 `lib/settings.php` 的默认值。随包的 `config.php`
把可覆盖的键都以注释形式列好了，要改哪个就解开哪一行 ——
**解开注释就等于把这个值固定下来，以后升级不再自动更新**，所以只解开真正要改的。

`tests/checkdb.php` 会告诉你当前哪些功能参数被 `config.php` 覆盖了，
「开台核对」页底部也会注明免核对规则用的是默认值还是你的配置。

### 对 PHP 扩展的要求

只需要 **`pdo_mysql` 或 `mysqli` 其中之一**，有哪个用哪个，默认的
`driver => 'auto'` 会自动选（优先 PDO，没有就用 mysqli）。两条路功能完全一致。

所以如果你的环境只装了 `mysqli`，**不需要为了这个程序去改 php.ini**。

不依赖 `mbstring`、`iconv`、`intl`、`curl`、`openssl` 等任何其他扩展。

环境诊断（完全独立，不依赖任何数据库扩展，一定跑得起来）：

```bash
php tests/env.php
```

它会报出：PHP 读的是哪个 php.ini、扩展目录在哪、目录里有哪些数据库扩展文件、
哪些扩展加载了、程序能不能跑、以及出 500 时去哪里找真正的错误。

> **命令行和 Web 服务器往往用不同的 php.ini**，所以请在浏览器里也访问一次
> `tests/env.php`，对比两边报出的路径 —— 改错文件是"改了没效果"最常见的原因。

### 部署后先跑体检

```bash
php tests/checkdb.php
```

也可以直接用浏览器访问 `tests/checkdb.php`。它会依次检查：
PHP 扩展是否齐全、配置是否填好、数据库能否连上、账号是不是只读、
需要的 6 张表在不在、实时表有多大、数据时间范围、
以及实跑近 7 天的四条统计查询并报出耗时和结果抽样。
全程只执行 SELECT。

出问题时它会直接指出是哪一环，比在页面上看一句"查询失败"好定位得多。

### 逻辑自检（不需要连数据库）

```bash
php tests/selftest.php
```

## 三、统计口径

以下口径均已用你导出的 **89,139 条真实账单（2024-01-22 ~ 2026-08-13，931 个营业日）** 验证。

### 时段划分

| 时段 | 范围 | 判定依据 |
|---|---|---|
| 白天 | 08:00 – 17:30 | **开台时间** `order_start_time` |
| 晚上 | 18:00 – 次日 02:00 | 同上 |
| 时段外 | 其余时间 | 同上 |

- **营业日**：凌晨 02:00 之前的单归入**前一天**。晚市跨零点的单子不会被算到第二天。
- 全库实测：白天 51,178 单 / 晚上 37,948 单 / 时段外 **13 单**（全部在 17:30–17:53 之间）。
  时段外的单子会**单列一行**显示，不会凭空消失，保证 `全天 = 白天 + 晚上 + 时段外` 恒等。
- 已验证：**逐日单独查询之和 == 整段一次查询**，区间边界无重复、无遗漏。

时段的默认值在 `lib/settings.php`（`day_start` / `day_end` / `night_start` / `night_end`），
要改就把同名的键写进 `config.php` 覆盖。
改 `night_end` 时必须同步改 `day_cut_hour`，两者要保持一致。

### 营业额

以 **`actual_amount`（实收）** 为准。页面同时列出金额构成便于对账：

```
应收 should_amount = 原价 original_amount + 折扣 discount_amount   ← 折扣以负数记录
实收 actual_amount = 应收 should_amount   − 退单 return_amount
```

真实数据 5000 条抽样，两条恒等式 5000/5000 成立。

> **税额是价内含税**（IVA 10%），已经包含在实收里，页面单独列出仅供参考，**不要再加上去**。

### 人数

**必须按 `order_head_id` 去重。** 一张单被拆成多个 `check_id` 结账时，
每个 check 都重复写了相同的 `customer_num`。

实测（最近 90 天）：直接 `SUM(customer_num)` = 24,758 人，
按订单去重后 = **22,125 人**，直接相加会**虚高 11.9%**。

程序内层子查询按 `order_head_id` 归并：人数取 `MAX`，金额取 `SUM`，时间取 `MIN`。

### 菜品点单

明细表里混着大量非菜品行，以下全部剔除：

| 剔除对象 | 条件 | 说明 |
|---|---|---|
| 送厨房标记行 | `menu_item_id = -3` | 形如 `**999 Enviado 19:16**` |
| 付款方式行 | `menu_item_id = -4` | 形如 `EFECTIVO` |
| 退菜 | `is_return_item = 1` | |
| 套餐 / 做法子项 | `condiment_belong_item <> 0` | 实测为**负数**（如 `-77`），可用开关重新计入 |
| 做法 / 口味项 | `menu_item.item_type = 1` | 如 `S/Pepino`（不要黄瓜），共 172 个，不是菜 |
| 数量为 0 的行 | `quantity <= 0` | |

> ⚠️ **`is_send` 不是"赠送"，是"已送厨房"** —— 84% 的正常菜品都是 1。
> 千万不要拿它当赠送过滤，否则菜会被全部滤光。程序没有使用这个字段。

菜品金额 = `SUM(actual_price × quantity)`。
**不使用 `sales_amount`** —— 该字段在历史明细和实时明细里实测全是 `0` 或 `NULL`。

### 岗位

**岗位 = `print_class`（打印分类／出品部门）**，共 14 个：
Kitchen、Sushi 1–7、POS 1、POS 2、bebidas、热菜、铁板、油锅。

> ⚠️ **明细表自带的 `print_class` 字段是废的** —— 历史明细（2024-01）和实时明细（2025-07）
> 抽样中该字段全部是 `0` 或 `NULL`，从来没有真实岗位 ID。
>
> 因此岗位来自 **`menu_item.print_class`**：单独查一次 `menu_item`（666 行）和
> `print_class`（14 行）两张小字典表，在 PHP 内存里做映射，**不与大表 JOIN**。
>
> 副作用：如果某道菜后来被调整过所属岗位，历史统计会按**当前**岗位归类。

## 四、性能设计

需求要求"数据表单独统计，非必要每次只统计一张表"，实现如下：

| 页面 | 查询的表 | 说明 |
|---|---|---|
| 营业额统计 | `history_order_head`（+ 可选 `order_head`） | 无任何 JOIN |
| 菜品统计 | `history_order_detail`（+ 可选 `order_detail`） | 无任何 JOIN |
| 岗位单量排名 | `history_order_detail`（+ 可选 `order_detail`） | 无任何 JOIN |
| 开台核对 | `order_head` + `order_detail` | 各查一次，无任何 JOIN |
| 字典 | `menu_item`、`print_class` | 各几百行，单独查询，内存映射 |

- 营业额与菜品统计**完全分开**，互不影响，不会一次拉起两张大表。
- 时间条件写成 `列 >= :from AND 列 < :to`，**不对索引列做任何函数运算**，
  可以吃满 `ids_order_start_time`（账单头）和 `idx_order_time`（明细）两个现有索引。
- 菜品排行**只查一次表**：一次取回全部菜品 × 时段的汇总（约 600 菜 × 3 时段 ≈ 1800 行），
  Top10 / Bottom10 / 各岗位排行全部在 PHP 内存里算出，不再回数据库。
  这也绕开了 MySQL 5.5 没有窗口函数、无法写 `ROW_NUMBER()` 分组取 TopN 的限制。
- 岗位单量排名同样**只查一次明细表**，且只返回十几行汇总。
  难点在于「单量」是 `COUNT(DISTINCT order_head_id)`，按菜品分别统计再相加会重复计
  （同一张单点了同岗位两个菜就会算两次），必须在数据库端按岗位分组算；
  可岗位又只能来自 `menu_item.print_class`，明细表里没有。
  解决办法是把「菜品ID → 岗位」映射编译成 SQL 里的 `CASE WHEN menu_item_id IN (…) THEN 岗位`
  表达式 —— 666 个菜品分成十几个 IN 列表，SQL 文本几 KB，MySQL 处理 IN 列表很快。
  这样既不做 JOIN、又不用把上万行明细拉回 PHP。所有 ID 都强制 `(int)` 转换后拼接。
- 日期跨度上限 92 天（约 3 个月），默认在 `lib/settings.php` 的 `max_range_days`，可在 `config.php` 覆盖。

数据量参考：931 个营业日共 89,139 单，单日最多 228 单，3 个月约 9,000 单，压力很小。

页面底部会显示每条查询的耗时，方便你确认实际表现。

## 五、⚠️ 需要你确认的一件事：实时表的数据量

"包含当天未日结数据"选项会额外查询 `order_head` / `order_detail` 两张实时表。
**这两张表没有时间索引**（只有主键），如果它们在日结后不清空、长期累积，
这个查询会变成全表扫描。

你导出的 `order_detail` 样本里有一条 `order_detail_id = 1387928`、
时间是 `2025-07-14` 的记录 —— 也就是一年多前的数据仍在实时表里。
请跑一下这条（只读）语句确认：

```sql
SELECT COUNT(*) AS rows_now,
       MIN(order_time) AS oldest,
       MAX(order_time) AS newest
FROM order_detail;
```

- **几千行以内** → 保持默认，勾选"包含当天未日结数据"没问题。
- **几十万行以上** → 建议平时**取消勾选**该选项（只查历史表），只在需要看当天实时数据时临时勾上；
  或者请 POS 厂商给 `order_detail.order_time` 和 `order_head.order_start_time` 加索引
  （这属于改表结构，本程序不会做，需要你自己决定）。

历史表 `history_order_head` / `history_order_detail` 索引齐全，不受此影响。

`lib/db.php` 里 `PdoDriver` 和 `MysqliDriver` 两个类实现同一个 `DbDriver` 接口，
上层代码只认 `Db::select()`，完全不感知底层用的是哪个扩展。
mysqli 不支持 `:name` 命名参数，驱动内部会转换成 `?` 位置参数 ——
转换时会跳过单引号字符串，避免把 `'08:00:00'` 里的冒号误当成占位符（有专门的测试覆盖）。

## 七、开台核对

对付这种情况：**开了 4 位客人，却一份套餐都没打，或者只打了 2 份** —— 直接就是漏收钱。

页面列出当前**已开桌、未结算**的每一台，逐台比对开台人数与已打的套餐份数：

| 核对结果 | 含义 |
|---|---|
| 一致 | 套餐份数 = 人数 |
| 套餐打少了 | 份数比人数少，**大概率漏打** |
| 未打套餐 | 一份都没打 |
| 套餐打多了 | 份数比人数多 |
| 未填人数 | 开台时没填人数，无法比对 |
| 免核对 | 外带（Llevar）这类台，本来就没有人头套餐，不参与核对 |

**排序：需要核对的台在最前，其次是已人工确认的，然后是一致的，免核对的排最后；每一档内部按桌号排**
（自然排序，2 排在 10 前面，纯数字桌号排在 `Llevar` 这类文字桌号之前），
方便照着桌号一台台核。同时给出「已点菜品」「当前金额」「已开台时长」帮助判断 ——
刚开台还没下单的台也会显示成「未打套餐」，看时长和菜品数就能区分。
开台超过 `open_table_warn_hours`（默认 4，在 `lib/settings.php`）小时仍未结账的会把时长标红，
方便发现忘了关的台。

> **只点单品、不吃自助的客人本来就不会有套餐**，这类会显示成「未打套餐」，属正常。
> 请结合金额和菜品数判断，不要一律当成漏打。

### 外带等不用核对的台

外带（Llevar）没有堂食人数，也不会点按人头的自助套餐，拿人数去比对只会一直报
「未打套餐」，纯属噪音。这类台判为**免核对**：不计入「需要核对的台」，
在列表里压暗排到最后，也不提供「确认」按钮（服务端同样拒绝对它盖章）。

默认规则在 `lib/settings.php`，按**桌号**匹配，大小写不敏感，`*` 是通配符：

```php
'no_combo_tables' => ['Llevar*', '外带*'],
```

`Llevar*` 能匹配 `Llevar`、`LLEVAR 2`、`llevar-03`。要再排除吧台、打包台，
加一行 `'Barra*'` 之类即可。匹配是**整体匹配**，`A-Llevar` 不会命中。

> 要改就在 `config.php` 里写同名的键覆盖（见「配置分两层」）。
> 页面底部会注明当前用的是默认值还是你的配置。
> 真要「所有台都核对」，在 `config.php` 里明确写成空数组 `[]`。

也可以按 `order_head.eat_type` 排除（比桌号更准，但要先确认本店的取值），
在 `config.php` 里写：

```php
'no_combo_eat_types' => [3],   // 默认留空 []，拿不准就别动
```

> ⚠️ `eat_type` 填错会把堂食台也一并跳过。改完先到核对页看看「免核对」的台数对不对 ——
> 页面底部会列出当前生效的两条规则，卡片上也会显示免核对的台数。
>
> 新增外带台、改了桌号命名规则后记得回来更新，否则那些台会一直报「未打套餐」。

### 人工确认（并桌之类的情况）

并桌会让一张单人数很多却没有套餐，核对结果显示成「未打套餐」，但其实是正常的。
这类台可以点「确认」标记掉，之后不再计入「需要核对的台」。

- **要点两下**：先点「确认」，该行原地展开「确定？[确定][取消]」，再点一次才生效 ——
  防止手机上误触。整个流程走服务端，不依赖 JS
- **存在当前登录会话里**（PHP session），**不写数据库** —— 本程序始终只读
- 默认 `ack_hours`（6，在 `lib/settings.php`）小时后自动失效；**退出登录即清空**；换一台设备要重新确认
- **该台人数或套餐份数一变，确认立即作废**，重新回到待核对状态 ——
  补打了套餐、加了人，都不会被旧的确认盖住
- 只是又点了几个菜、金额变了，确认**仍然有效**（否则会一直重复确认）
- 顶部有「全部撤销」，可一次清空

> 确认是按浏览器存的：经理手机上确认过，收银台电脑上仍会提示。
> 这是 session／cookie 这类客户端方案的固有限制 ——
> 要跨设备共享就必须落库，那会打破只读约束。

技术细节：确认时记下当时的「人数:套餐份数」指纹，渲染页面时比对，对不上就当没确认过。
提交走 POST + CSRF 校验，并且会再次比对提交上来的指纹与服务端当前值 ——
如果从页面渲染到点确定之间数据变了，会拒绝并提示重新核对，不会拿旧状态盖章。

### 哪些菜品算「按人头的套餐」

由 `combo_item_ids` 决定（默认在 `lib/settings.php`，可在 `config.php` 覆盖），
默认是从菜单表查出来的 6 个自助餐套餐：

```php
'combo_item_ids' => [1290, 1490, 1590, 1890, 2390, 2590],
```

成人餐和儿童餐都要列进去 —— 4 位客人可能是 2 大 2 小，加起来仍应是 4 份。

BOX 1–18 与 COMBO S/M/L/XL（`item_type = 3`）**默认不计入**：那是打包组合，
不是按人头点的，算进来会让核对失真。

> ⚠️ **换季改菜单、新增套餐后记得更新这个清单**，否则核对结果会失真。
> 页面底部会折叠列出当前生效的清单和各自单价，其中在菜单表里查不到的 ID 会被标出来。

### 数据来源

只查两张实时表，各一次，不做 JOIN：`order_head` 拿开台列表，
`order_detail` 一次算出每台的套餐份数与菜品总数。

「未结算」判定为 `order_end_time IS NULL`。如果这个假设在你的系统里不成立
（页面始终空白），把范围切到「实时表里的全部订单」就能看到实际情况，
该模式会多一列显示每单是否已结算。

> `order_detail` 没有 `order_head_id` 索引，这条查询会全表扫描一次。
> 实时表通常只装当前未日结的数据，问题不大；若该表很大（见第五节），这一页会偏慢。

## 八、岗位单量排名

「单量」= 该岗位出品**涉及了多少张单**（多少桌）。一张单里同岗位点了几个菜也只算一单。

同时给出这几个指标，可任选一个作为排名依据：

| 指标 | 含义 |
|---|---|
| 单量 | 该岗位涉及多少张单（`COUNT(DISTINCT order_head_id)`） |
| 出品份数 | 数量合计（`SUM(quantity)`） |
| 出品笔数 | 明细行数 |
| 金额 | `SUM(actual_price × quantity)` |

并按白天 / 晚上 / 时段外拆开显示。

> **各岗位单量之和会大于总账单数**，这是正常的 —— 一张单通常会经过多个岗位
> （比如既有热菜又有饮料），每个岗位都会各自计一单。要看真实的总账单数，
> 请以「营业额统计」页为准。
>
> 同理，「菜品数」是各岗位各自的去重菜品数，也不能相加，所以合计行留空。

两类特殊分组会单独成行，不和正常岗位混在一起：

- **未分配岗位** —— 菜品在 `menu_item` 里存在但没配 `print_class`
- **菜品已从菜单删除** —— 历史订单里有这个菜品 ID，但 `menu_item` 里已经查不到了

## 九、已知口径说明

- `status` 字段全库只有一个值 `2`，无法用来区分作废单，程序**不做**该字段过滤。
- `rvc_center` 只有一个营业点（`Comedor`），因此没有做营业点维度。
  将来若开分店，需要在 `Biz::buildSalesSql()` 里加 `rvc_center_id` 分组。
- `eat_type`：`0` = 堂食（78,535 单），`3` = 外带 `Llevar`（10,597 单），
  另有 `1`/`2` 共 7 单。页面提供筛选，默认统计全部。
- 全库有 1,672 张 `actual_amount = 0` 的账单（占 1.9%，多为开台未消费）。
  默认计入账单数，可勾选"排除 0 元账单"剔除。

## 十、常见问题

**`Undefined constant PDO::MYSQL_ATTR_MULTI_STATEMENTS`**

这个常量由 pdo_mysql 扩展注册，扩展没加载时它就不存在。程序已改成
`defined()` 判断后再使用，缺了不影响功能 —— 真正拦截多语句的是 SQL 里的分号检查。

**`could not find driver` / 没有可用的 MySQL 扩展**

pdo_mysql 和 mysqli 都没加载。**启用 `extension=mysqli` 就够了**，不必启用 pdo_mysql。

**启用 `extension=pdo_mysql` 后 Web 服务器返回 500**

不用管它 —— 把这行改回注释状态，只要 `extension=mysqli` 是启用的，程序照常工作。

如果你确实想查 500 的原因，跑 `php tests/env.php`，它会列出扩展目录里实际有哪些
文件。Windows 上最常见的原因是 `C:\php…\ext\php_pdo_mysql.dll` 不存在，
或者 dll 的线程安全模式（TS/NTS）与 PHP 本体不匹配。

**页面能打开但查不出数据**

先跑 `php tests/checkdb.php`，第 7 节会显示数据库里实际的数据时间范围 ——
很可能是查询的日期超出了这个范围。
